# Architecture and security notes

The application is a single-process Python HTTP server backed by SQLite. Local usernames resolve to configured demo roles after PBKDF2 password verification; optionally, an OIDC authorization-code/PKCE flow authenticates a provider subject and resolves it through an app-owned subject allowlist. Random opaque session IDs are stored only as hashes, with expiry and server-side tenant/role mapping. Cookies are HttpOnly and SameSite=Strict; POST endpoints require a CSRF token. The local accounts remain demo-only, and the OIDC path has only mock-provider integration tests, not a live provider certification. All data access uses bound SQL parameters. Document retrieval first filters by tenant and then by the document's current role ACL; permissions are therefore checked at query time rather than encoded only in an index.

The router is multinomial Naive Bayes trained from hand-labeled synthetic utterances. It chooses `keyword`, `dense`, `hybrid`, `sql`, or `tool`. The local dense option is TF-IDF cosine over tokens and is not a neural embedding. Hybrid combines lexical and cosine ranks using RRF; a simple overlap feature reranks. This makes the training and routing real and inspectable while avoiding network dependencies.

The workflow uses deterministic application code for SQL and action selection. SQL is limited to parameterized templates and user/tenant scopes. Tool effects are SQLite-backed; ticket creation is idempotent and returns a persisted identifier. A high-risk mock VPN revocation is initiated by support/admin, approved by a distinct tenant approver, reauthorized at execution, and verified against the persisted access grant. Mixed policy/device questions carry subquestions and a dependency list in the response trace. Response objects pass the versioned structural contract in `schemas/response.schema.json`; this does not establish claim entailment. Evidence is returned with source IDs and retrieval provenance. A raw evidence-support feature is mapped through an isotonic calibrator fitted on a fixed synthetic training split; a training-selected confidence threshold can abstain from low-confidence answers. `experiments/evaluate_confidence.py` executes 18 authored scenarios, checks expected status/evidence/answer fragments, fits on 12 cases, and evaluates on a six-case holdout. This is a runnable calibration pipeline, but not credible production calibration. Imported instruction-like lines are filtered from excerpts; this is a narrow defense, not a general prompt-injection solution.

Document ingestion accepts bounded TXT, Markdown, PDF, and DOCX input, extracts heading/paragraph/table structure, and records per-chunk source locations. New versions are indexed before activation; failed ingestion preserves the previous active version. Deletion deactivates the current document and its chunks. This is a synchronous local pipeline with no OCR or background queue.

## Security boundary

All local demo accounts share a configurable known-by-default password. OIDC is generic and requires operator configuration, HTTPS endpoints, client registration, and an exact subject allowlist; it has not been exercised against a live provider. The service binds to loopback and is for local synthetic data only. Do not expose it to a network or use real data. There is no password reset/MFA lifecycle, distributed or persistent rate limiting (only basic in-process throttles), encryption-at-rest, production audit retention, or isolation boundary suitable for hostile users. Role checks are examples rather than a full permission policy. The VPN revocation tool is a local mock and must not be connected to real access infrastructure.

## Reliability boundary

The server has no worker queue, distributed transaction coordination, external model timeout handling, or service-level instrumentation. SQLite is suitable for the local demonstration only. Version history and retrieval deletion propagation are implemented. Selective prediction has only a synthetic fitted calibrator; representative reviewed labels and live answer generation are still needed. There is no claim entailment model or generator failure recovery. Docker and CI configuration are present but container build could not be exercised here. These gaps should be closed before any production deployment.
